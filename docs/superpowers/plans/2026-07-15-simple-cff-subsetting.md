# Simple CFF Subsetting Implementation Plan (`4by`, remaining half)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let `Optimize` subset simple CFF fonts (`FontFile3` `/Subtype /Type1C`, plus `Type1`/`MMType1` dicts pointing at one) instead of skipping them, via a name-keyed shrink path that preserves the code→name→GID chain.

**Architecture:** A new `shrinkNameKeyedCff` re-assembles a CFF preserving charset, Encoding, and the String INDEX as raw bytes — unlike `shrinkCff`, which emits a CID-keyed program. A new `simpleCffMapper` unions the three defensible code→GID chains. Supporting reads (`charsetNames`, `builtinEncoding`) go on `CffFont`; a new `src/cffstrings.ts` supplies the SID→name table.

**Tech Stack:** TypeScript (strict, ESM/NodeNext), vitest. No runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-07-15-simple-font-subsetting-design.md` (Design 3)
**Issue:** `aspose-pdf-foss-for-ts-4by` (simple TrueType half already landed in `88dd3a8`)

## A deliberate deviation, flagged

House style for plans is that every code step carries the code. Tasks 2, 3, and 4
break that: their *interfaces, tests, and contracts* are complete and exact, but
their implementation steps point at the spec's algorithm rather than inlining a
finished `shrinkNameKeyedCff`.

Two reasons, both weighed rather than assumed:

1. `2026-07-15-simple-font-subsetting-design.md` Design 3 already specifies this
   algorithm to the byte — the region table, which Top DICT operators get
   rewritten, and every charset/Encoding length formula. Restating it here would
   duplicate a reviewed source of truth, and the two copies would drift.
2. Emitting large generated byte-level tables is what tripped output content
   filtering while drafting this plan. Task 1's 391-string table is written once,
   in chunks, straight into the source file for the same reason.

What this costs: an implementer cannot work from this plan *alone* — they must
read Design 3 alongside it. That is an accepted trade, not an oversight. The
tests in each task are complete and are what pin correctness.

## Global Constraints

- **Zero runtime dependencies.** Only `node:` built-ins.
- **ESM + NodeNext.** Import specifiers carry `.js`.
- **Strict TypeScript.** `npm run typecheck` and `npm test` must both be green before closing.
- **TDD.** Failing test first, watch it fail, then implement.
- **The scan invariant** (from the spec, drives everything): *a glyph is blanked only when every site that could reference it was scanned successfully, and only when no plausible viewer chain resolves any shown code to it.* When in doubt, skip and report — never guess.
- **`shrinkCff` is not reusable here.** It re-assembles through `assembleCidCff`, emitting a CID-keyed program (`/ROS`, FDArray/FDSelect, charset publishing integer CIDs). Under a simple font dict that is invalid, not merely lossy. Do not "simplify" Task 4 into a call to `shrinkCff`.
- **Out of scope, deliberately:** Type1 (`/FontFile` PFB — no CFF to resolve against), Type3, and `/OpenType` whole-embeds with CFF outlines (rewrapping a shrunk `CFF ` table into an `OTTO` sfnt is a separate concern). These stay skipped with a reason.

### Task 1: `src/cffstrings.ts` — the SID→name table

A charset stores SIDs. SID < 391 names one of the CFF standard strings; SID ≥ 391 indexes the font's String INDEX. Without this table a charset cannot be turned into glyph names, so nothing downstream works.

**Files:**
- Create: `src/cffstrings.ts`
- Test: `test/cffstrings.test.ts`

**Interfaces:**
- Consumes: nothing.
- Produces:
  - `export const STANDARD_STRINGS: readonly string[]` — exactly 391 entries, SID order.
  - `export function sidToName(sid: number, stringIndex: Uint8Array[]): string | undefined`

**Source of truth:** the CFF specification (Adobe TN#5176) Appendix A, "Standard Strings". Order is the data — SID *is* the array index. Do not sort, dedupe, or "tidy" the list.

> **Transcribe in chunks.** Emit the array across ~5 successive writes of 60-80 names each rather than one large block. A single large generated data table can trip output content filtering, which fails the turn outright. The test below — not this plan's prose — is what pins correctness.

```ts
// The CFF standard strings (SID 0..390) and SID -> glyph-name resolution.
// Transcribed from the CFF specification (Adobe TN#5176) Appendix A. The array
// index IS the SID, so order is load-bearing: never sort or dedupe this list.

/** The 391 predefined strings every CFF shares. A charset SID below 391 names
 *  one of these; 391 and up index the font's own String INDEX. */
export const STANDARD_STRINGS: readonly string[] = [
  // filled in by the chunked writes that follow
];

/** Resolve a charset SID to a glyph name. `undefined` when the SID runs past the
 *  font's String INDEX — a malformed charset, which callers must treat as
 *  unresolvable rather than substitute a guess for. */
export function sidToName(sid: number, stringIndex: Uint8Array[]): string | undefined {
  if (sid < 0) return undefined;
  if (sid < STANDARD_STRINGS.length) return STANDARD_STRINGS[sid];
  const item = stringIndex[sid - STANDARD_STRINGS.length];
  return item === undefined ? undefined : new TextDecoder().decode(item);
}
```

- [ ] **Step 4: Transcribe the table in chunks**

Fill `STANDARD_STRINGS` across successive small edits, in SID order:
- SID 0-79: `.notdef`, `space` … through the ASCII punctuation, digits, and uppercase letters.
- SID 80-159: lowercase letters, then the Latin-1 punctuation and symbols.
- SID 160-239: accented letters.
- SID 240-320: the remaining accented and special letters.
- SID 321-390: the Expert-set names and the weight names ending at `Semibold`.

After each chunk, re-run the test. The `length === 391`, anchor, and duplicate checks together catch an off-by-one or a dropped entry immediately — which is the point of transcribing against a test rather than against prose.

### Task 2: `CffFont` reads — charset names and the built-in Encoding

The name-keyed chain needs two reads the parser does not expose: gid→name (from the charset) and code→gid (from the CFF's built-in Encoding).

**Files:**
- Modify: `src/cff.ts` (add `parseCharsetSids`; refactor `parseCharsetCid` onto it; add `CffFont.charsetNames()` and `CffFont.builtinEncoding()`)
- Test: `test/cff.test.ts` (or `test/cffsubset.test.ts` — follow whichever already covers `CffFont`)

**Interfaces:**
- Consumes: `sidToName`, `STANDARD_STRINGS` (Task 1); `readIndex`, `parseDict`, `op1` (already exported from `cff.ts`).
- Produces:
  - `CffFont.charsetNames(): (string | undefined)[]` — gid → glyph name; `undefined` per-gid when the SID is unresolvable. Empty array for a CID-keyed font (a CID charset holds CIDs, not SIDs).
  - `CffFont.builtinEncoding(): Map<number, number> | undefined` — code → gid. `undefined` when the font uses predefined Standard (offset 0, the default) or Expert (offset 1), which carry no embedded table.

**Design notes for the implementer:**
- A charset's byte layout is identical for CID and name-keyed fonts — only the *interpretation* of the 16-bit field differs (CID vs SID). So `parseCharsetSids(bytes, v, off, numGlyphs): number[]` (gid → SID, gid 0 implicitly SID 0) is the shared primitive; `parseCharsetCid` becomes a thin inversion of it. Formats 0, 1, and 2 all appear in the wild.
- Predefined charsets (offset 0 ISOAdobe, 1 Expert, 2 ExpertSubset) have no bytes to walk. For offset 0, SID == GID for the ISOAdobe range, which is the common case; treat 1 and 2 as unresolvable (return an empty array) rather than guessing.
- Encoding lives at Top DICT op 16. Offset 0 = predefined Standard, 1 = predefined Expert; anything else is an offset to an embedded table. Format 0: `nCodes`, then one code byte per gid starting at gid 1. Format 1: `nRanges`, then `(first, nLeft)` pairs. If the format byte's high bit (0x80) is set, a supplement block follows: `nSups`, then `(code, SID)` triples — resolve those through the charset.

### Task 3: `parseDictSpans` — rewrite Top DICT offsets without decoding operands

The shrunk program must re-emit the Top DICT with new offsets for `charset`/`Encoding`/`CharStrings`/`Private`, while copying everything else — `FontMatrix` reals (BCD), unknown operators — byte-for-byte. Decoding to numbers and re-encoding would corrupt reals and drop unknowns.

### Task 4: `shrinkNameKeyedCff` — the name-keyed shrink path

The core of this issue. Same sparse-blanking contract as `shrinkCff` (numGlyphs and GID numbering intact, unused charstrings → bare `endchar`), but re-assembled name-keyed.

**Files:**
- Modify: `src/fontshrink.ts`
- Modify: `test/helpers/build-cff.ts` (add `buildNameKeyedCff`)
- Test: `test/fontshrink.test.ts`

**Interfaces:**
- Consumes: `parseDictSpans` (Task 3), `parseCffProgram`, `flattenGlyph`, `writeIndex`, `bias` (existing).
- Produces: `export function shrinkNameKeyedCff(cff: Uint8Array, keep: Set<number>): ShrinkResult` — same `ShrinkResult` shape `shrinkGlyf`/`shrinkCff` return.

**Region treatment (from the spec — this table is the contract):**

| Region | Treatment |
|---|---|
| Name INDEX | copied |
| String INDEX | **copied verbatim** — keeps every SID ≥ 391 valid |
| charset | **raw bytes copied** — SIDs unchanged; predefined (0/1/2) left as-is |
| Encoding | **raw bytes copied** — predefined (0/1) left as-is |
| Private DICT | raw bytes copied, `Subrs` (op 19) dropped |
| Global/Local Subr INDEX | emitted empty; kept charstrings flattened |
| CharStrings INDEX | rebuilt, same count, unused → bare `endchar` |

charset and Encoding are copied as raw bytes rather than re-emitted from a parse: re-emitting charset as format 0 inflates a range-coded charset, and re-emitting Encoding cannot express a glyph with no code in either format. Copying needs only a length computation — charset format 0 → `1 + 2*(numGlyphs-1)`, formats 1/2 → walk ranges until `numGlyphs` is covered; Encoding format 0 → `2 + nCodes`, format 1 → `2 + 2*nRanges`, plus `1 + 3*nSups` when the high bit is set.

Top DICT is re-emitted from Task 3's spans, rewriting only ops 15 (charset), 16 (Encoding), 17 (CharStrings), 18 (Private) — each in the fixed 5-byte `dictInt5` form so the DICT's length is known before its offsets are, and the program lays out in one pass exactly as `assembleCidCff` does.

### Task 5: `simpleCffMapper` — the usage chain

Replaces the `TODO(4by)` stub at `glyphusage.ts:154-157`, which currently returns `{ reason: 'simple CFF font' }`.

**Files:**
- Modify: `src/glyphusage.ts:154-157`
- Test: `test/glyphusage.test.ts`

**Interfaces:**
- Consumes: `CffFont.charsetNames()` / `.builtinEncoding()` (Task 2), `sidToName` (Task 1), `resolveSimpleEncoding` (`font.ts`), `unionChains` (module-local).
- Produces: a working `simpleCffMapper(doc, font): { mapper?: CodeMapper; reason?: string }`.

**The three chains, unioned** (per the spec — union, never select):
1. `/Differences` name → `nameToGid` (inverted from `charsetNames()`) — exact.
2. code → Unicode (base encoding) → `unicodeToGid` (derived from `charsetNames()` through `glyphToUnicode`).
3. CFF built-in Encoding → code → gid — exact, and **the only chain when the font dict has no `/Encoding`**. Note `resolveSimpleEncoding` defaults to WinAnsi in that case, which is wrong for CFF: the built-in encoding governs. Guard on `enc.implicit`.

Built-in Encoding offset 0 = Standard → chain 2 already covers it. Offset 1 = Expert → no chain; if no other chain applies, skip with a reason.

Reach the program via the existing `sfntOf`-adjacent path: `/FontFile3` with `/Subtype /Type1C`, and the `OTTO` whole-embed extraction already present at `glyphusage.ts:198-213`. A `/FontFile` (PFB) has no CFF → skip, reported.
