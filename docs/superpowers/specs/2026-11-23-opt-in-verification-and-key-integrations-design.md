# Opt-in verification and key integrations

This scope records the design for `chp0.5` against TypeScript `3ccf6e85` and the Go snapshot `dfa75dbf`. It builds on the authenticated revision reopens delivered in `chp0.1`. The three integration features have separate API boundaries and fixture tests.

## Priority and sequencing

| Issue | Priority | Work | Sequencing |
| --- | --- | --- | --- |
| `chp0.7` | P1 | Prevent plaintext fallback when signing protected PDFs | Contain the confirmed confidentiality defect before first-write encrypted signing. |
| `chp0.8` | P2 | Authenticate revocation evidence before reporting status | Validate existing offline and callback evidence before enabling discovery. |
| `chp0.9` | P3 | Discover revocation endpoints through opt-in bounded transport | Build on `chp0.8`. |
| `chp0.10` | P3 | Support external RSA keys for PubSec recipients | Build on `chp0.1` authenticated reopens. |
| `chp0.11` | P3 | Sign newly authored password-encrypted PDFs on first write | Build on `chp0.7`. |

`chp0.6` covers credentials and encrypted DSS data for later authoring operations. Its acceptance criteria are separate from the initial plaintext fallback.

### Confirmed signing behavior

An in-memory probe created a one-page password-encrypted PDF, reopened it with the synthetic password, edited its title, and signed it. The output opened with no password, the edited title remained readable, and the signature verified. Independent probes confirmed the behavior for AES-128 and AES-256 while unedited controls retained the encrypted prefix. A second probe requested encryption at `Save()` after signing a new document and received the same cached plaintext bytes. [Signing path](../../../src/document.ts) · [Plaintext signing serializer](../../../src/serializer.ts) · [Existing encrypted signature integration tests](../../../test/sign-encrypted.test.ts)

Containment can use a typed, pre-mutation refusal for protected documents that would take the plaintext full-rewrite path. An explicit encryption override on sealed signed bytes must also produce a typed refusal. Regression tests should exercise `Sign`, `Certify`, the unedited encrypted append control, and unchanged bytes and fields after rejection.

## Revocation endpoint discovery

`VerifySignatures` already accepts explicit offline evidence and `getOCSP` and `getCRL` callbacks. It can read revocation material from the PDF DSS. The Go snapshot exposes opt-in discovery and an injectable fetcher. Go's default client provides a useful baseline for request selection and timeouts. For TypeScript, require an injected transport in the first release so an application controls outbound routing. [TypeScript verification options](../../../src/sigverify.ts) · [Go revocation options and transport](https://github.com/aspose-pdf-foss/Aspose-PDF-FOSS-for-Go/blob/dfa75dbfb300e6eb5a8e5d2199f81d07ed602916/revocation.go#L73-L156)

**Evidence prerequisite.** The current combined checker verifies an OCSP signature against embedded candidate certificates or the issuer and matches the target certificate ID. The candidate loop does not establish responder authorization. The CRL status path also needs freshness and applicability checks. Require a cryptographically matched issuer, exact CertID, and an authorized response signer bound to `ResponderID`. Apply certificate usage and time checks, including a finite maximum age for OCSP responses missing `nextUpdate`. Accept fresh, applicable, full direct-issuer CRLs with validated signing usage. Use a bounded DER parse at the wire boundary. Inconclusive evidence contributes `unknown` while the PDF digest, CMS signature, and certificate path retain independent verdicts. [Current evidence checker](../../../src/revocation.ts) · [RFC 6960 response acceptance and signer authorization](https://www.rfc-editor.org/rfc/rfc6960.html#section-3.2) · [RFC 5280 CRL validation](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.3)

**Discovery and precedence.** Add an explicit verification option pairing a destination policy with a transport. The existing verification evidence path evaluates offline and callback material first. Discovery is eligible after successful digest and CMS checks and a cryptographically matched issuer. For each signer, read OCSP AIA URI entries and direct full-name CRL distribution point URIs in certificate order, deduplicate, and try approved OCSP endpoints before CRLs. Use a single-cert DER OCSP POST and a CRL GET. A verified decisive answer ends lookup for that signer. The first feature covers the current signer evidence path in `VerifySignatures`. Path retrieval, historical or chain-wide online checks, and DSS authoring have separate workflows. [RFC 5280 authority information access](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.2.1) · [RFC 5280 CRL distribution points](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.13) · [RFC 6960 transport](https://www.rfc-editor.org/rfc/rfc6960.html#appendix-A)

**Network policy.** Verification has zero discovery requests by default. Require a normalized exact-origin allowlist and HTTPS by default. Plain HTTP requires separate explicit policy. Reject redirects, URL credentials, and unsupported schemes. The injected transport must enforce destination restrictions at connection time, including against disallowed private, loopback, and link-local destinations, and honor an abort signal. Apply a shared deadline and request and concurrency limits to discovery across all signers, with a decoded response-byte cap checked during streaming. Reject oversize bodies. A deliberately noncooperative adapter must still leave the verifier with a bounded return and no additional scheduled work. Initial proposed ceilings are 10 seconds, eight requests, two concurrent requests, 512 KiB per OCSP response, and 4 MiB per CRL. Test lower limits with injected controls and use synthetic destinations.

**Fixtures.** Use an independently issued, non-self-signed leaf with mixed AIA and CRL distribution point names, duplicates, and signer and issuer certificates. Check the OCSP request against separate encoder output. Use signed PDF fixtures and fake streaming transport for zero-request defaults, evidence precedence, rejected integrity and issuer checks, ordered fallback, denied origins, redirects, deadlines, cancellation, decoded byte limits, and attempt limits across signers. Include independently issued valid, unauthorized, wrong-CertID, stale, and wrong-scope evidence. ## External RSA recipient keys

TypeScript opens PubSec files with a local `KeyObject` and certificate or PKCS#12. Its signer callback is a different credential path. Go's certificate entry point accepts `crypto.Decrypter`, and the reviewed envelope implementation uses it for RSA PKCS#1 v1.5 key transport. The TypeScript boundary is a synchronous RSA recipient adapter, since opening, baseline reads, and revision reopens are synchronous. Promise-based providers would require an async design across these paths. [TypeScript recipient normalization and reopen](../../../src/document.ts) · [Go certificate open](https://github.com/aspose-pdf-foss/Aspose-PDF-FOSS-for-Go/blob/dfa75dbfb300e6eb5a8e5d2199f81d07ed602916/document.go#L191-L221) · [Go `crypto.Decrypter`](https://pkg.go.dev/crypto#Decrypter)

Add a certificate-plus-callback branch to `OpenOptions.recipient`. Give the callback a copy of the matched envelope's wrapped content-encryption key and the recognized transport algorithm. The library matches issuer and serial, validates algorithm and parameters, opens CMS content with the returned key, and derives the PDF key from the original recipient bytes. A callback failure for an addressed envelope terminates the open. Retain the adapter privately with the normalized certificate for authenticated reopens, respect the original load limits, and document that later operations may invoke it again. Keep the local RSA, EC, and PKCS#12 entry points available. [CMS recipient decoding](../../../src/cms.ts) · [PDF PubSec decryption](../../../src/pubsec.ts) · [RFC 5652 key transport](https://www.rfc-editor.org/rfc/rfc5652.html#section-6.2.1)

For Go parity, scope RSA PKCS#1 v1.5 to callers who explicitly provide a provider capable of that mode with safe failure behavior. Require exact algorithm identifiers and uniform typed refusal for unsupported input. External OAEP needs explicit hash, MGF1, and label validation. Keep it as a separate algorithm follow-up. [RFC 3560 OAEP parameters](https://www.rfc-editor.org/rfc/rfc3560.html#section-3)

**Fixtures.** Use a Go-produced AES-128 PubSec PDF for independent adapter parity and keep local OAEP and EC controls. Go's AES-256 producer also uses AES-256 inside CMS, whereas the reviewed TypeScript CMS reader supports AES-128-CBC there. A Go AES-256 case therefore also requires separate content-cipher coverage. Test matched and unrelated recipients, same issuer with a different serial, unsupported algorithms, returned key lengths, errors during revision reopening, mutation isolation of callback input, encrypted incremental saves, and signature verification across revisions. [Go CMS envelope implementation](https://github.com/aspose-pdf-foss/Aspose-PDF-FOSS-for-Go/blob/dfa75dbfb300e6eb5a8e5d2199f81d07ed602916/pubsec.go) · [Independent envelope tests](../../../test/pubsec-openssl.test.ts)

## First-write encrypted signing

Go creates an unsigned encrypted base, reopens it with the specified password, and adds the signature in an incremental revision before writing the final file. Use the same architecture for freshly authored TypeScript documents. Offer explicit password-based encryption configuration on the signing operation before the byte image is sealed. Reuse the classic encrypted writer and incremental signature machinery. Preserve the AES-256 default and the currently supported Standard Security Handler algorithms. Apply the same explicit configuration to approval and certification signing. [Go encrypted first signature](https://github.com/aspose-pdf-foss/Aspose-PDF-FOSS-for-Go/blob/dfa75dbfb300e6eb5a8e5d2199f81d07ed602916/sign_incremental.go#L25-L52) · [Current incremental writer](../../../src/incremental.ts)

Serialize the completed authored graph into an in-memory encrypted base and reopen it under the selected credentials. Append the signature using the reopened graph and key. The append preserves the byte prefix and file identifiers, encrypts ordinary strings and streams, and writes direct raw CMS `/Contents`. Compute `/ByteRange` and the digest against the exact stored byte image. Commit the signing graph, retained credentials, and signed bytes together only after a successful placeholder fill. Provider failures, a signature exceeding its reserved capacity, and edits during a pending operation must leave the document retryable. Subsequent incremental operations require matching object numbers and authenticated byte context. A documented save and reopen boundary can provide that context for the first release. [TypeScript placeholder layout](../../../src/sigplaceholder.ts) · [ISO 32000-2 byte-range notes](https://pdf-issues.pdfa.org/32000-2-2020/clause12.html#128-digital-signatures)

**Fixtures.** Check distinct user and owner passwords, incorrect-password refusal, approval and certification, visible or prepared fields, stable base encryption and identifiers, and failure and retry. Verify the pending signed bytes, save and reopen, and verify again. qpdf checks password enforcement, encrypted content, and xref structure. An independent CMS check over the stored byte range or a separate PDF signature reader checks the signature itself. Include a Go-produced encrypted signed PDF as a read-side interoperability fixture.
